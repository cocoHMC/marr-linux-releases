# marr-linux-releases

## Completing work

- Carry the requested outcome through the next authorized steps. Make reasonable, reversible implementation choices and explain consequential assumptions. Ask only for a real access blocker, a material scope decision, or an action whose target or effect is not authorized; continue independent work meanwhile.
- Preserve the user's selected model, provider and reasoning effort. Use supported runtime options and task-appropriate defaults when no choice was specified; do not silently add paid services or change provider settings.
- Read relevant code and instructions, then implement. Reuse existing logic and preserve caller contracts unless the task changes them. Prefer readable names and direct control flow over code golf, unnecessary helpers or speculative abstractions.
- Check current ownership and Git state. Use beta directly for one writer; use temporary isolation only when concurrency needs it. Agents own integration and verified cleanup. Preserve unrelated work and avoid duplicate sessions or validation.
- Review the requested outcome before reporting completion. State what changed, the verified remote beta commit or actual delivery outcome, pending preparation and any concrete blocker. Make the final report understandable without progress updates. Repository instructions do not grant production, publication or destructive-action authority.

This repository distributes Linux release information and artifacts. Preserve published artifact identities and download links. Source edits do not authorize replacing binaries or publishing a release.

## Validation

Follow [TESTING.md](TESTING.md). Build and integrate completed work into `beta`
without authoring or running tests. Agents handle optional temporary branches,
integration and verified cleanup. Start testing and polish only when the owner
asks to prepare beta; release only when asked to push to production. Reuse
existing approval and report the verified remote beta or delivery outcome.
